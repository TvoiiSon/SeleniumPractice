1. Что оказалось проще/сложнее на Selenium по сравнению с Playwright?
- Playwright при создании браузера со scope session создает одно окно браузера на все тесты, но каждый тест получает чистый контекст браузера без кук и других (т.е. контекст в playwright со scope function), а Selenium в свое время создает также одно окно со scope session, но на каждый тест не приходит чистый контекст (т.е. Selenium не чистит контекст перед новым тестом) — пришлось руками дописывать очистку кук/localStorage/sessionStorage в фикстуре driver
- Playwright при помощи get_by_role создает ленивый указатель, а у Selenium из коробки такой возможности нет — find_element ищет элемент сразу, в момент вызова, и если его еще нет на странице, сразу же кидает NoSuchElementException. Пришлось писать свою обертку LazyElement, которая резолвит локатор (обычный или через функцию-предикат) только в момент действия, через WebDriverWait
- Playwright сам матчит текст по подстроке и по нескольким источникам (placeholder, aria-label, текст элемента) через один get_by_role/get_by_placeholder. В Selenium под каждый источник текста — свой XPath (@placeholder, @aria-label, text()), и если угадать не тот атрибут — локатор просто не найдет элемент без явной ошибки о причине. Например, кнопка "Очистить поиск" визуально показывает "✕", а сам текст "Очистить поиск" лежит только в aria-label — с Playwright это было бы не важно, а в Selenium сломало тест
- Загрузка файлов: у Playwright set_input_files() сам резолвит относительный путь, а у Selenium send_keys() на <input type="file"> требует абсолютный путь — с относительным падает с "File not found"
- Мока сетевых ответов (page.route()/expect_response()) в Selenium нет как готового API — но нашелся driver.network (BiDi), из которого пришлось самому собирать аналог: driver.network.add_response_handler для наблюдения за ответом и driver.network.add_request_handler + request.provide_response(...) для подмены тела и статуса ответа

2. Где возникала нестабильность, как решалась?
- Локатор аватарки в шапке (avatar_button) был рассчитан только на инициал одной буквой (span с текстом), а после того как у тестового аккаунта появилось загруженное фото, шапка стала рендерить <img alt="Avatar"> вместо буквы — из-за этого предикат переставал находить элемент вообще, и все фикстуры, завязанные на авторизацию, начинали падать. Починил так, чтобы предикат сначала искал <img alt="Avatar">, и только если его нет — букву-инициал
- Сразу после запуска браузера (до первой навигации) страница показывает about:blank, и попытка почистить localStorage на этой странице падает с SecurityError — решилось тем, что в фикстуре driver сначала идет переход на BASE_URL, и только потом чистка storage
- "Ленивые" локаторы через функцию-предикат сначала вызывались один раз напрямую, без ожидания — если элемент еще не успел отрисоваться, сразу падало исключение вместо повторной попытки. Решилось тем, что и обычные локаторы, и функции-предикаты теперь одинаково оборачиваются в WebDriverWait внутри одного метода _resolve_element
- События из BiDi (ошибки JS, сетевые ответы) приходят асинхронно по WebSocket, а не сразу в момент вызова — пришлось не просто читать результат сразу после действия, а ждать его через WebDriverWait, пока он не появится в списке пойманных событий

3. В каких ситуациях какой инструмент предпочтительнее?
- Playwright лучше, когда нужно быстро получить стабильные тесты без написания своей инфраструктуры — автоожидание перед каждым действием, гибкий поиск по доступному имени и встроенный мок сети уже есть из коробки
- Selenium лучше, когда важна не эта конкретная задача, а более широкая экосистема — больше языков биндингов, больше готовых интеграций с CI/Selenium Grid, и не привязан к своим версиям браузеров (можно гонять на уже установленном в системе браузере)
- Selenium предпочтительнее, если нужен низкоуровневый контроль над протоколом (тот же BiDi/CDP напрямую) — Playwright прячет эти детали за высокоуровневым API, и если появляется нестандартный кейс, до низкого уровня добраться сложнее
